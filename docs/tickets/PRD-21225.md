## Requirement understanding

One line: Review MFA enrollment, devices, and admin activity via Cisco Duo's identity security platform.

Restatement: the reporter (Mandy Du, parent epic PRD-21190 "MCP Epic") wants a Cisco Duo MCP connector that
lets an agent look at three things on a customer's Duo account: (1) the MFA enrollment state of users, (2)
the MFA devices (phones / hardware tokens / security keys) associated with those users, and (3) administrative
activity on the account. The ticket body is a single sentence plus a reference link to the MCP-catalog page
for this connector (`https://conduit.wyre.ai/plugins/cisco-duo`); that page adds no detail beyond the sentence
itself and the generic "first-time setup takes about 20-40 minutes" boilerplate — confirmed by fetching it, no
tool-level or capability-level specifics are listed there. Success looks like: an agent can list/inspect users
and their enrolled MFA factors, drive the pre-enrollment / enrollment-verification flow, and pull a record of
admin actions taken on the account — all through this MCP server.

## Product design

### Goals / Non-goals

- Goal: an agent can retrieve a Duo account's administrator activity log (who did what administrative action,
  and when) through this MCP server, using the same per-request credential model as every other tool here.
- Goal: confirm (not re-build) that MFA enrollment and MFA-device review are already fully served by the
  existing 28 tools, so the next reader doesn't re-open that question.
- Non-goal: re-adding any of the other 14 removed categories (`Administrators`, `Administrative Units`,
  `Policies`, `Endpoints`, `Registered Devices`, `Passport`, `Trust Monitor`, `Settings`, `Custom Branding`,
  `Account Info`, `Bulk Operations`, `Integrations`, `Desktop Authenticators`, standalone `Bypass Codes`) or the
  other five log variants (`activity` v2, `authentication` v1/v2, `offline_enrollment`, `telephony` v1/v2) —
  none of those map to a capability this ticket names; re-adding them would be scope creep past the ticket's
  own words, which is exactly the kind of over-build the 2026-08-04 trim was undoing.
- Non-goal: this ticket does not ask to block/unblock devices, manage endpoints, or otherwise administer the
  account — only to *review* enrollment, devices, and activity.

### Acceptance criteria

- **AC1**: Given an agent calls `tools/list` on the running server with valid credential headers, Then the
  tool set includes a tool that returns Duo administrator-activity log entries (who performed the action, what
  the action was, and when), in addition to the 28 tools already present.
- **AC2**: Given an agent calls that tool with a valid time range and valid `X-Duo-Ikey` / `X-Duo-Skey` /
  `X-Duo-Api-Host` headers, When the Duo account has administrator activity in that range, Then the tool
  returns the log entries as structured JSON (not an error).
- **AC3**: Given an agent calls that tool with one or more of the three credential headers missing, Then the
  call is rejected the same way every other tool on this server already is (401, `required_headers` listing
  `X-Duo-Ikey`, `X-Duo-Skey`, `X-Duo-Api-Host`) — no new, inconsistent auth path.
- **AC4**: Given the Duo API returns an error (4xx/5xx) for the log request, Then the tool returns the same
  structured error envelope shape (`error.code` / `error.message` / `error.retryable`) every other tool uses,
  not a raw exception or a different shape.
- **AC5**: Given MFA enrollment and MFA-device review (the other two capabilities this ticket names), Then no
  code change is needed — this is a design-time confirmation, not a user-facing AC, and is recorded so a later
  reader doesn't reopen it: the 28 existing tools already serve it (see Current state).

### Open questions

- **[unblocking, decided by assumption]** "Devices" in the ticket's one line is read as *MFA factor devices*
  (phones, hardware tokens, security keys/WebAuthn — the things Duo itself calls "devices" in its own
  end-user-facing MFA UI), not Duo's separate "Registered Devices" / "Endpoints" product area (which is about
  device-trust/health and blocking non-compliant machines, not MFA). The ticket's own phrasing — "MFA
  enrollment, devices, and admin activity" — reads as three facets of one MFA-review workflow, not a
  device-trust/endpoint-management ask, and it never mentions blocking, trust, compliance, or endpoints. If
  this assumption is wrong and the reporter actually wants Registered Devices / Endpoints coverage, that is a
  separate, larger addition (10 more tools across two removed categories) and should come back as a new
  ticket with that stated explicitly, not be guessed into this one.
- **[non-blocking]** Whether to also re-add the modern unified `GET /admin/v2/logs/activity` endpoint (which,
  per Duo's documentation index, folds authentication/telephony/administrator events into one feed) in
  addition to the administrator-specific `GET /admin/v1/logs/administrator` endpoint chosen here. Not done in
  this design because the ticket's own word is "admin activity," not "all activity," and the v1 endpoint is the
  one purpose-built for exactly that (see Tech design §3 for why it, not the v2 unified log, was chosen). Can
  be added later as its own tool if a user asks for the broader feed.

## Tech design

### Conclusion

Add one new tool, `duo_logs_administrator_logs` (`GET /admin/v1/logs/administrator`), in a new
`src/duo_mcp/tools/logs.py` module, registered the same way every other category is. No other file's runtime
behavior changes. This is a straight re-add of one tool from the project's own pre-trim history — not a new
design from scratch — following the current (post-SOP) coding pattern used by every other tool in the repo.

### Where the current implementation lives

- `src/duo_mcp/server.py:122-137` — `create_mcp_server()` imports each tool-category module and calls
  `mod.register(mcp, client_factory)` in a fixed tuple (`groups, phones, tokens, users,
  webauthn_credentials`); a new `logs` module is added to that import and that tuple, nowhere else.
- `src/duo_mcp/tools/groups.py:1-52` — the category module to copy the shape of: `Annotated[..., Field(...)]`
  parameter typing, `@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))` for read-only calls,
  `dump_json_capped()` for the return value, `except DuoError as e: return e.to_envelope()` for errors. This is
  the current, post-SOP-compliance pattern (see `tools/_common.py:1-7` for `NO_TOKEN`, and
  `src/duo_mcp/api_client.py:67-75` for `DuoError.to_envelope()`).
- `src/duo_mcp/tools/logs.py` at commit `67e529d` (`git show 67e529d:src/duo_mcp/tools/logs.py`, the last
  commit before the 2026-08-04 trim) — the pre-trim implementation of `duo_logs_administrator_logs`. It predates
  the SOP-compliance pass (`2d10cc7`, "Comply with new vendor-mcp SOP (v1.0, 2026-08-18): error envelopes,
  retry/timeout with re-signed HMAC per attempt, annotations, instructions, tests"), so it uses the old
  `json.dumps(..., indent=2)` / `return f"Error: {e}"` shape, not the current one — the new implementation
  should follow `groups.py`'s current shape, using the old file only for the endpoint path, parameter name, and
  the fact that this exact tool was already built once and the developer at the time stated it was "originally
  extracted from Duo's own official Postman collection ... cross-referenced against the live
  `duo.com/docs/adminapi` documentation" (`README.md:137-142`, same sourcing methodology applies to the removed
  `logs.py`).
- `README.md:91-328` — the single source of truth for scope, auth, and the tool table; it needs the three
  updates listed in Change list.
- `tests/test_tools.py:15-44` (`EXPECTED_TOOLS`) and `:46-62` (`READ_ONLY_TOOLS`) — the structural test that
  pins the exact tool set and their read-only/required-param shape; adding a tool here fails this test until
  the dicts are updated, which is the point (red before green).

### Data & API contract

**New MCP tool**

```
duo_logs_administrator_logs(mintime: str | None = None) -> str
```

Request (vendor side): `GET https://<X-Duo-Api-Host>/admin/v1/logs/administrator?mintime=<mintime>` (HMAC-SHA512
signed per `api_client.py`'s existing `_canon_params` + signing logic; `mintime` omitted from the query string
entirely when `None`, matching every other optional-param tool in this repo, e.g. `groups.py`'s `limit`/
`offset`).

Response (success, 200) — passed through via `dump_json_capped()`, shape per Duo's own `logs/administrator`
response schema (array of log entries; confirm exact field names — e.g. `timestamp`, `username`, `action`,
`description` — against `duo.com/docs/adminapi` during implementation, same as every other tool's `body: dict`
fallback pattern used elsewhere in this repo for undocumented-at-design-time shapes).

Response (error) — same structured envelope every tool returns:
```json
{"error": {"code": "unauthorized", "message": "...", "retryable": false}}
```
via the existing `_STATUS_TO_CODE` mapping in `api_client.py` (401/403 → `unauthorized`, 404 →
`not_found`, 429/5xx → retryable, etc. — unchanged, reused as-is).

Missing-credential response — identical to every other tool, from the existing gateway middleware
(`server.py`'s `GatewayTokenMiddleware`), not from the new tool itself:
```json
{"error": "Missing credentials", "message": "This server requires the X-Duo-Ikey, X-Duo-Skey, and X-Duo-Api-Host headers", "required_headers": ["X-Duo-Ikey", "X-Duo-Skey", "X-Duo-Api-Host"], "optional_headers": []}
```

**Backward compatibility**: purely additive — one new tool name, no change to any existing tool's request or
response shape. Nothing to migrate.

### Key flow / sequence

1. Agent calls `tools/list` → sees `duo_logs_administrator_logs` alongside the existing 28.
2. Agent calls `duo_logs_administrator_logs` with `X-Duo-Ikey` / `X-Duo-Skey` / `X-Duo-Api-Host` headers and an
   optional `mintime`.
3. `GatewayTokenMiddleware` (unchanged) validates the three headers are present → 401 with `required_headers`
   if not.
4. `client_factory()` builds a per-request `DuoClient` from the contextvar (unchanged).
5. Tool calls `client.request("GET", "/admin/v1/logs/administrator", params={"mintime": mintime})` (new line,
   existing method) → `DuoClient` computes the HMAC-SHA512 signature and makes the signed request (unchanged
   signing/retry logic).
6. Success → `dump_json_capped(result)` returned. Duo error → `DuoError` raised → `e.to_envelope()` returned.

### Non-functional

- **Idempotency/concurrency**: the tool is read-only (`GET`); no idempotency concern. Credential isolation is
  unchanged — still per-request via `contextvars` (`server.py:14-24`), so concurrent calls from different
  tenants/customers never share a `DuoClient` instance.
- **Performance**: single GET per call, same timeout/retry budget as every other tool
  (`api_client.py:29-32`, `_TIMEOUT` / `_RETRYABLE_STATUS` / `_MAX_RETRIES` — unchanged, reused). Response size
  is capped by the existing `dump_json_capped()` (20,000-char budget, `_json.py:11`), same as every other tool.
- **Security**: credentials are read from headers only, never persisted, never logged — unchanged, this tool
  introduces no new credential-handling path (SOP's "three ironclad rules," unaffected by this change).
  Administrator-activity logs can themselves contain sensitive data (what another admin changed, when) — this
  is read access, gated by the same three headers as every mutating tool in this server, so no new privilege
  boundary is introduced; whoever holds valid `X-Duo-Ikey`/`X-Duo-Skey` already has Admin API access to this
  and more (per Duo's own permission model, referenced generically in the webfetch of
  `duo.com/docs/adminapi`: "read authentication, offline access, telephony, and administrator action log
  information" is one Admin API permission grant among several).
- **Multi-tenant isolation**: unaffected — isolation here is "whichever Duo account the caller's own
  `X-Duo-Ikey`/`X-Duo-Skey`/`X-Duo-Api-Host` headers point to," identical to every other tool; this server has
  no cross-tenant state to leak (stateless HTTP, no shared client instance, per `README.md:83-87`).
- **Observability**: no new logging added beyond what every other tool already relies on (the MCP gateway's
  own call audit log, per the MSPbots Connector feature list in `README.md:56-60` — "every tool call is
  logged"); this server itself does not add structured logging per tool, consistent with every existing tool.

### Rollout & rollback

Single-repo, single-tool addition. No feature flag needed (every other tool in this server ships the same way
— there is no precedent for flagging individual tools, and nothing here is destructive or behavior-changing for
existing callers). Release order: `any` — this repo has no cross-repo dependency for this change (no other
MCP or platform repo calls into `duo-mcp`'s tool set). Rollback is `git revert` of the merge commit; no data
migration exists to roll back.

### Test strategy

- **Unit/structural** (existing suite, extended): `tests/test_tools.py::test_tools_list_snapshot` — already
  asserts the full tool-name set, required-param set, and `readOnlyHint` annotation for every tool via
  `EXPECTED_TOOLS`/`READ_ONLY_TOOLS`; adding the new tool to those two dicts is both the test change and the
  spec the implementation must satisfy (red until the tool exists and is registered, green once it does).
- **Already covered, no new test needed**: `tests/test_middleware.py` (credential-header gating) and
  `tests/test_tools.py::test_error_envelope_mapping` (status-code → error-code mapping) are both tool-agnostic
  — they test the shared `GatewayTokenMiddleware` and shared `DuoError.to_envelope()` respectively, so the new
  tool is automatically covered by both once it goes through `client_factory()` / `DuoError` like every other
  tool.
- **Manual, needs a real Duo account**: calling `duo_logs_administrator_logs` against a live Duo Admin API
  account and confirming the response contains actual administrator-action entries (or a valid empty result if
  the account has none) — the same kind of live self-test the repo's README already records having done for
  three other tools (`README.md:277-293`). Per `mcp-track.md` §2.5/§3 ("lacking a vendor test account does not
  count as a blocker"), lacking a real Duo account does not block this ticket from shipping; it is recorded as
  "needs a real vendor account" in the test cases below and left for whoever has one to execute.
- **Regression**: the structural snapshot test (`test_tools_list_snapshot`) is itself the regression guard for
  the other 28 tools — it fails loudly if this change accidentally touches their names, required params, or
  annotations, since the dict comparison is exact-set.

### Effort & breakdown

0.5–1 person-day. Single new tool, following an existing pattern, in a repo whose test suite already pins the
exact shape to hit. The range's uncertainty is entirely in confirming the exact response field names and the
`mintime` unit (seconds vs. milliseconds) against live `duo.com/docs/adminapi` content during implementation —
not in the amount of code. One sub-task is enough; no further breakdown needed for a change this size.

### Risks & dependencies

- **Risk**: the pre-trim `logs.py`'s parameter shape (`mintime: str | None`) may not match the Admin API's
  current documented contract exactly (Duo's docs may have changed since whenever that file was first
  written, and this design could not fully confirm the live schema — see Current state and the two web-fetch
  attempts noted there, which returned only partial/truncated content). Mitigation: implementation should
  re-confirm the parameter name, type, and unit against `duo.com/docs/adminapi` directly (or against Duo's
  Postman collection, `https://github.com/duosecurity/duo_postman_collection`, the same source the rest of
  this repo was built from per `README.md:137-139`) before shipping, and adjust the docstring/signature if it
  has changed.
- **Risk**: "admin activity" could, per the Open Questions above, mean the broader unified v2 activity log
  instead of (or in addition to) the administrator-specific v1 log. Mitigation: documented as a non-blocking
  Open Question with an explicit, defensible choice (v1 is the one purpose-built for exactly "admin activity";
  v2 is a different, broader ask the ticket doesn't make).
- **Dependency**: none on other tickets or repos. This is a self-contained, single-repo change.
